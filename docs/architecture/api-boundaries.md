# Hoborouter API Boundaries (PROPOSED — pending human review)

Three surfaces: client AI proxy (`/v1/*`), workspace console API (`/api/*`), payment webhooks (`/webhooks/*`). Plus the internal boundary to CLIProxyAPI (CPA) and the usage collector. Elysia 2 routes; all JSON; Better Auth sessions for console, `sk-hbr-` Bearer keys for `/v1/*`.

## 1. Client AI proxy — `/v1/*` (thin, OpenAI-compatible)

Auth: `Authorization: Bearer sk-hbr-…` → lookup hash → workspace + key status. Rate-limited per key.

| Route                       | Behavior                                                                                                                                                                                 |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/models`            | Published model bindings for the workspace only; CPA aliases never exposed. Static list, no upstream call.                                                                               |
| `POST /v1/chat/completions` | Thin proxy. **Phase 2: `stream:false` only — `stream:true` rejected 400 until Phase 3 abort policy.** Reserve → dispatch to CPA → pipe body → correlate `cpa_trace_id` → settle/UNKNOWN. |
| `POST /v1/responses`        | Same pipeline. Thin translation only — **CPA owns protocol translation**; gateway maps public model → CPA alias and forwards.                                                            |
| `GET /v1/models/{id}`       | Binding detail (prices, capabilities).                                                                                                                                                   |

Gateway-added response headers: `X-HBR-Request-Id` (gateway_request_id). **`X-HBR-Billing` is emitted exactly once, at response start, with the fixed value `reserved` — it is NEVER later mutated and NEVER takes another value at response start** (HTTP/SSE headers cannot change after the first byte; UNKNOWN/hold is determined only after dispatch, so it can never appear in the response header). If a failure occurs **before** response start (validation failure, 402 insufficient funds, upstream error before any byte), **no `X-HBR-Billing` header is emitted at all**. Final billing state — including `unknown`/`hold` — is read via `GET /api/requests/:id`. Inbound `X-CPA-TRACE-ID`, `X-Request-Id`, and `OpenAI-Request-Id` from clients are **stripped/untrusted**; only CPA response headers on an explicit allowlist are copied from the private upstream. `X-Request-Id` fallback identity is UNVERIFIED — not used for billing correlation.

**Money pipeline per request (strict order):**

1. Validate + estimate → snapshot price → in one transaction: insert request + reservation rows and run the canonical reservation `UPDATE wallets SET reserved = reserved + :cap, version = version + 1 WHERE id = :wallet_id AND balance - reserved >= :cap` (affected rows `= 1` required; 0 → 402 on insufficient available funds; `balance` is the actual posted balance, `available` derived).
2. **Commit** (durability point).
3. Dispatch to CPA. **No retry after dispatch** — any ambiguity = `unknown`, funds held, surfaced for review (duplicate upstream spend risk; see architecture.md §2). Paid-path CPA config: `routing.retry.request-retry = 0`, `bootstrap-retries = 0`, verified by Phase 0 probe (provider-attempt count = 1); **if the pinned release provides no way to disable failover/retries, it is rejected for paid traffic.**
4. Response start → `X-HBR-Billing: reserved` (estimate, not settlement; emitted once, never mutated; no header at all if failure precedes response start).
5. Verified usage event correlated → idempotent settle (one transaction; event assignment via `settlement_usage_events` `UNIQUE(usage_event_id)`): debit ≤ cap from **balance**, release the **full cap** from **reserved** (precondition `reserved >= cap`; available rises by `cap − charge`), checked integer arithmetic (`charge ≥ 0`, `charge ≤ cap`), **plus the terminal CAS `reservations.status held|unknown → settled` with affected rows `= 1` required (0 → already terminal: persist usage only, no wallet/ledger mutation)** — CAS, wallet update, settlement row, and ledger debit commit together. Releasing an unused hold writes **no** refund cash row. Final state via `GET /api/requests/:id`.
6. No verified usage or ambiguous event (NULL execution UUID, ambiguous trace mapping) → status `unknown`, funds held per human policy. **Never silently settled; never auto-settled; never claimed billable.**

**Streaming client abort:** gateway stops piping, marks `client_abort`, funds held, usage reconciled only if a verified event arrives. **[OPEN — HUMAN] abort billing policy; streaming route may be built but not launched as guaranteed-billed before that decision.**

**Launch gating:** if no deterministic usage mapping (stable, uniquely-enforced provider-event identity) on pinned CPA release → paid routes return 503 `billing_unverified` until verified, or a **separate, explicitly approved bounded-loss process** is signed off (human-decided cap + monitoring; this tolerates and monitors unbilled/underbilled VND but does **not** enable auto-settlement or summing of ambiguous events).

## 2. Console API — `/api/*` (Better Auth session)

- **Auth:** `POST /api/auth/*` (Better Auth routes), session cookie.
- **Workspaces:** CRUD `/api/workspaces`, members, roles.
- **Keys:** `GET/POST/DELETE /api/keys` — POST returns plaintext `sk-hbr-` **once**; never retrievable again; revocation is immediate.
- **Wallet:** `GET /api/wallet` (balance, reserved, available), `GET /api/ledger` (paginated, append-only view).
- **Payments:** `POST /api/payments` (create top-up order → mock provider link), `GET /api/payments/:id`. The **mock provider is development/demo only — behind an auth check and feature flag, disabled in production**; it emits payOS-shaped webhooks to `/webhooks/payments/mock`.
- **Models (instance admin):** `GET/POST/PUT /api/admin/models` — public name ↔ CPA alias mapping, VND prices; publishes immutable price snapshot. **Instance-admin only, global scope.** Separate from workspace model reads: workspace-scoped model visibility is served by `/v1/models` (key auth) and, in the console, by `GET /api/workspaces/:id/models` (read-only view of bindings enabled for that workspace, including global bindings). Disabled bindings stop serving immediately.
- **Usage/logs:** `GET /api/requests` (filter by model/status/date, Vercel-style logs table), `GET /api/requests/:id` (detail: reservation, usage events, correlation IDs, billing state including `unknown`/`hold`), `GET /api/usage/summary`.
- **Admin review (instance admin):** `GET /api/admin/unknowns`, `POST /api/admin/unknowns/:id/resolve` (**idempotent**: request carries a client-supplied `resolution_key` (UUID); partial unique index on resolution makes duplicate replays return the first result — 409 only on conflicting duplicate payloads; outcomes: **hold-release only or manual-settle with reason** — both perform a single terminal CAS `held|unknown` → `released`/`settled`; hold-release returns `reserved` to available, **no ledger row, not a cash refund**; manual-settle debits ≤ cap) → audit_log. Persisted in `unknown_resolutions` (data-model.md §2): one final resolution per request (`UNIQUE(request_id)`); insert/replay + terminal CAS + wallet/ledger mutation in one atomic `BEGIN IMMEDIATE` transaction keyed by `resolution_key` (concurrent same-key first-use serialized or rollback/reselect to guarantee replay); conflicting duplicate payload or any distinct-key resolution after the reservation is terminal → 409; ownership validated in-transaction (`reservation.gateway_request_id = resolution.request_id`, workspace/wallet scope checked).
- **Refunds (instance admin, separate route):** `POST /api/admin/refunds` — **separate post-settlement cash refund** of an already-posted charge, applied only to a `settled` reservation, referencing the original settle debit via `refund_operations.original_ledger_entry_id` (never blocked by terminal fencing); idempotent by client-supplied `operation_key`, one refund per original debit, conflicting retry → 409. In one `BEGIN IMMEDIATE` transaction: same-key replay returns the stored result (different `payload_hash` → 409); ownership of the original settle debit validated (reservation + wallet match); refund amount checked `0 < amount <= original debit amount` (checked integer arithmetic); wallet `balance` increased by the amount with `version` increment and overflow check (`reserved` unchanged); refund ledger row `balance_after` consistent with the wallet update; wallet + ledger + refund_operations commit together or none. NOT an `unknown_resolutions` outcome — a request may be refunded after its `manual_settle` resolution, which `UNIQUE(request_id)` would block. → audit_log. Late usage after release is persist-only, never settled. **[OPEN — HUMAN] resolution policy.** Instance-wide admin routes (model catalog global writes, CPA config) are a **separate role** from workspace admin.
- **AuthZ route matrix (enforced + tested per route).** Scope column: `ws` = workspace_id-scoped (row access restricted to the caller's workspace), `global` = instance-wide, no workspace filter. Instance admin is not implied by any workspace role and vice versa:

## 3. Payment webhooks — `/webhooks/*`

| Route                                     | Contract                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /webhooks/payments/mock`            | **Dev/demo only: auth check + feature flag, disabled in production** (internal network or test env). payOS-shaped payload (`code/desc/success/data{orderCode, amount, reference,...}`). **Signature: an internal mock-only HMAC-SHA256 contract — HMAC over a documented deterministic canonical encoding (sorted-key JSON: lexicographically sorted keys, separators `,`/`:`, UTF-8, no whitespace), hex-encoded, key = configured mock checksum key. This is NOT claimed to be payOS-identical**: payOS's real canonicalization (its signed `transaction_str`) is not verified from source; the mock contract exists only to exercise verify/reject paths and is replaced by the real provider contract at Stage 5. Required negative tests: invalid signature, amount mismatch, replay. |
| `POST /webhooks/payments/payos`           | Stage 5; same shape, real checksum key.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `POST /webhooks/payments/vnpay` / `/momo` | Stage 5+; VNPay HMAC-SHA512 IPN, MoMo HMAC-SHA256 — canonicalization re-verified at integration.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

Rules: verify signature → insert `payment_events` (unique on `(provider, provider_reference)`; `provider` column NOT NULL) → **idempotently** credit wallet via ledger via PaymentService (never write ledger from the handler inline) → respond 2XX only after durable accept → amount validated server-side against the order. Replay-safe; duplicate webhooks produce one credit. All webhook routes perform provider-specific signature + order + amount validation (see `docs/research/vietnam-payments.md`).

## 4. Internal boundary: gateway ↔ CLIProxyAPI

| Direction       | Mechanism                                                                                                                                     | Notes                                                                                                                                                                                                                                                                                                                                               |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Proxy traffic   | HTTP/SSE to `http://cpa:8317/v1/*`                                                                                                            | CPA `access.api-keys` holds a single gateway-internal key; never exposed to tenants.                                                                                                                                                                                                                                                                |
| Usage ingestion | Strict single poller: `GET /v0/management/usage-queue?count=N` (or v8 `/observability/usage/queue`)                                           | **Pop is destructive; persist to SQLite before next poll.** Retention 60s default → poll interval well under it. Do NOT mix `SUBSCRIBE` (suppresses queueing; slow subscriber = lost messages). Crash between pop and persist = accepted loss (bounded, counted).                                                                                   |
| Correlation     | `X-CPA-TRACE-ID` response header; usage payload `request_id` (trace ID, not execution UUID); `Record.RequestID` (execution UUID) when exposed | Two-ID mapping per architecture.md §5. Header coverage must be probed on pinned release (Phase 0 gate).                                                                                                                                                                                                                                             |
| Health          | `GET /healthz` (liveness only, unauthenticated)                                                                                               | Readiness via management `credentials/status` — must not retry-loop management auth (5 failures ≈ 30 min ban).                                                                                                                                                                                                                                      |
| Config          | v8 management endpoints, v8 field spelling only                                                                                               | Write via pinned release; snapshot committed to repo. **Reachability: `management.allow-remote: true` ONLY on the private Compose network, non-empty `management.secret-key`, no CPA port published to host/Internet, explicit firewall/network policy, Phase 0 auth test both directions** (localhost-only semantics are false across containers). |

**Responsibility split:** CPA = protocol translation, credentials, routing/retry/failover, lossy usage attestation. Gateway = tenancy, keys, money, idempotency, durability, honest labeling, correlation. **Paid-path CPA config: `routing.retry.request-retry = 0` and `bootstrap-retries = 0`, verified by probe (provider-attempt count = 1). If no way exists to disable retries/failover on the pinned release, that release is REJECTED for paid traffic**; upstream spend capped by provider quotas as backstop.

## 5. Cross-cutting

- **AuthZ:** every `/api/*` route scoped by workspace membership + role; `/v1/*` by key→workspace. No cross-workspace reads.
- **Errors:** structured JSON `{error: {code, message, request_id}}`; money errors use `402` (insufficient), `409` (conflict/duplicate), `503 billing_unverified`.
- **Validation:** all client input validated at trust boundary (Elysia schemas); VND amounts positive integers; `max_tokens` and estimation cap bounded (multiplier abuse — see new-api review invariants). Inbound client-supplied `X-CPA-TRACE-ID` / `X-Request-Id` / `OpenAI-Request-Id` headers stripped at the gateway (untrusted); only allowlisted CPA response headers forwarded.
- **Static UI:** SPA from `vp build` output built **under Node** (Vite+ requires Node engines); Bun is the runtime; same origin; no dashboard access to `/v1/*` bypass.
- **No AGPL code:** API shapes follow OpenAI conventions and our own contracts; new-api used as concept reference only.
